# Project Reflection

## 2026-10-15 — Let players choose the terminal language before play
**Context:** The terminal game showed Chinese-only messages across menus, betting, replay, coaching, and input errors. The user requested Chinese and English play, fewer emoji, and a README that reflects actual behavior.
**Decision:** Choose a language before the first game screen, translate terminal print/input output for the active session, and accept Chinese action and replay commands alongside existing English commands. Keep engine action values, history records, and public agent contracts unchanged.
**Reasoning:** A presentation boundary covers existing terminal flows without changing poker semantics or historical data. It also lets language-specific wording and decorative emoji be adjusted in one place.
**Tradeoffs:** The translation catalog must be maintained when new player-facing text is added. Proper names and user-entered text remain as entered rather than being translated.

## 2026-10-15 — Make computer opponents credible in terminal play
**Context:** The user approved reliability and evaluation work but called out that the computer players still feel unintelligent. The terminal game created default advanced AI opponents, while benchmark simulations assigned the named archetype profiles. The AI also received an absolute seat index even though its position model expects small-blind-relative order.
**Decision:** Assign distinct archetypes to terminal computer players, translate the existing public seat position at the built-in AI adapter, and measure the resulting decision distribution with the canonical benchmark before making broader policy changes.
**Reasoning:** The player-facing game should use the same tested behavior families as the evaluation loop. Correct position input is a concrete decision-quality defect, while profile labels make opponents more recognizable without claiming solver-level strength.
**Tradeoffs:** Position correction changes historical benchmark comparability and must be accompanied by a new artifact. Profile variety is not proof of stronger play; calibration warnings still require separate fixture-backed work. A later CO/BTN open-raise candidate passed a reduced diagnostic but failed the primary completion gate, so its policy change was rolled back while the failed artifact was retained as evidence.

## 2026-05-25 — Write post-Phase-3 roadmap before platform implementation
**Context:** Phase 3 is complete through Stage 3.5, and the first post-Stage 3.5 calling-station negative-equity call loop reached its reduced-artifact target. The project now has stronger benchmark gates, sanitized audit samples, public/private safety checks, and evaluation-agent templates, which makes external-agent and online-platform work more tempting.
**Decision:** Create a post-Phase-3 development roadmap and make the next active work evidence inventory, remaining poor/blunder triage, Builder/Hacker candidate-loop discipline, profile calibration prioritization, and headless/action API readiness. Keep WebSocket rooms, auth/accounts, external-agent runtime, and online multiplayer out of the active plan until explicit gates are met.
**Reasoning:** The long-term AI Poker Arena / Agent Poker Platform needs stable evidence and boundary contracts before public surfaces. The latest tuning result supports a narrow diagnostic improvement, not a broad strength claim, and Stage 3.2 still records calibration WARNs. A roadmap preserves the platform vision while preventing premature networking/runtime work from outrunning safety, evaluator, and action-engine readiness.
**Tradeoffs:** Visible platform progress is delayed again, and the next work is more documentation/evidence-heavy than product-visible. The benefit is a cleaner execution path: future platform work can start from named gates, pre/post benchmark evidence, public/private safety guarantees, and smaller action-driven engine slices.

## 2026-05-12 — Start Phase 3 with evaluation loop before platform work
**Context:** After the AI player evaluation follow-up fixes, the local trainer baseline is stable: full suite passes, smoke benchmarks have zero illegal actions, folded-player transcript leakage is fixed, and built-in AI profiles show non-zero style separability. This makes it tempting to move directly toward online rooms or external-agent surfaces.
**Decision:** Make Phase 3 an AI Evaluation Loop phase first. Formalize primary benchmark gates, profile calibration, poor/blunder audits, public/private safety gates, and repeatable evaluation-agent roles before implementing WebSocket rooms, public APIs, auth, accounts, or external-agent runtimes.
**Reasoning:** The long-term AI Poker Arena / Agent Poker Platform depends on credible, repeatable, privacy-safe evaluation more than on early networking surfaces. Strength, style fidelity, legality, and hidden-state safety need benchmark evidence and regression loops before platform claims can be trusted.
**Tradeoffs:** Visible platform features are delayed again even though the local contracts are stronger. The benefit is that future platform work can start from measurable AI quality and safety gates instead of ad-hoc smoke tests or overconfident GTO/platform claims.

## 2026-05-12 — Close Phase 2 with platform non-goals before implementation
**Context:** Phase 2 now has documented visibility rules, benchmark gates, decision/action/event boundaries, external-agent request/response stubs, executable tests for external-agent state safety, and machine-readable benchmark gate evaluation. The project is technically closer to online/API/WebSocket work, which increases the risk of starting platform code before scope is explicitly chosen.
**Decision:** Treat Phase 2 as complete only after adding platform non-goals and an explicit trigger for future platform work: visibility tests and benchmark gates must be documented and passing, external-agent stubs must exist, non-goals must be indexed, and the maintainer must choose a post-Phase-2 platform slice before implementation begins.
**Reasoning:** Contract evidence is valuable only if it prevents accidental scope creep. Separating “future platform readiness” from “platform implementation” keeps online rooms, auth, real-money surfaces, and solver/GTO claims out of the local trainer hardening phase.
**Tradeoffs:** This delays visible platform features even after the contract scaffolding is ready. The benefit is a cleaner handoff into any future platform plan, with fewer chances to overclaim benchmark meaning or leak private state through rushed public surfaces.

## 2026-05-11 — Start Phase 2 with contract-hardening before platform work
**Context:** Phase 1 completed the local AI trainer credibility foundation: built-in AI behavior is less trust-breaking, benchmark runs are seeded/multi-seed capable, transcript samples preserve public-card safety, and trainer feedback stays local and cautious. The next tempting step is online rooms or external-agent integration, but the visibility and benchmark contracts are not yet strict enough for public platform surfaces.
**Decision:** Make Phase 2 a contract-hardening phase first: define public/private state visibility, benchmark acceptance gates, decision/action/event boundaries, external-agent contract stubs, and platform non-goals before implementing WebSocket rooms, public APIs, auth, accounts, or external-agent runtimes.
**Reasoning:** External agents and online adapters multiply the cost of hidden-card leaks, ambiguous benchmark claims, and unstable legality boundaries. Locking the contracts while the system is still local keeps `DecisionProvider`, `ActionValidator`, `EngineEvent`, and `ExternalAgentState` aligned before platform work depends on them.
**Tradeoffs:** Platform-visible features are delayed. The benefit is a clearer safety and evaluation baseline for any later AI Poker Arena work, with fewer chances to retrofit privacy, benchmark semantics, or non-goal language after public surfaces exist.

## 2026-05-08 — Introduce Sprint 3 engine event boundary before renderer replacement
**Context:** After Sprint 2, `game.py` still mixed state mutation, CLI output, AI action delay, history, and benchmark behavior. The project needed an event-oriented seam before external agents or online rooms could safely reuse the engine.
**Decision:** Add `EngineEvent` as a structured event contract, mirror core events from `game.py` without removing existing prints, add a first `TerminalEventRenderer`, let headless simulations optionally collect events, make AI action delay injectable, and define an immutable external-agent state contract that separates private hole cards from public player state.
**Reasoning:** Event mirroring gives tests and adapters a stable contract while preserving current terminal play. Keeping private cards separate in the future-facing state contract reduces the risk of leakage when external agents or online rooms are introduced.
**Tradeoffs:** The CLI still has direct prints in `game.py`, so renderer replacement remains incremental. Headless simulations can collect events, but existing benchmark summaries still use history records until the event stream fully covers all needed analytics.

## 2026-05-08 — Adopt AGENTS.md-centered documentation system
**Context:** The repository had a root-level project index and several root-level user/history documents, while `AGENTS.md` defines `docs/` as the stable home for permanent project documentation and root docs as only `AGENTS.md`, `CLAUDE.md`, and `README.md`.
**Decision:** Treat `AGENTS.md` as the single source of truth for agent instructions, create the required core docs under `docs/`, reuse the existing project index as `docs/index.md`, move user/history docs under `docs/`, and keep `CLAUDE.md` as a shim to `AGENTS.md`.
**Reasoning:** This gives future agents a deterministic session-start contract, reduces duplicated root-level documentation, and keeps durable project context, decisions, plans, reports, and conversation logs in predictable locations.
**Tradeoffs:** Some historical references still mention old root filenames as part of prior reports/plans; current operational links were updated, but old historical wording is preserved when it describes past work.

## 2026-05-08 — Finish Sprint 2 before online room work
**Context:** Sprint 2 evolved from individual slices into a complete foundation plan covering provider boundaries, benchmark isolation, metric fidelity, profile aggregation, AI tuning, and a headless-engine boundary spike.
**Decision:** Treat Sprint 2 as complete only after the action boundary, headless simulation, machine-readable benchmark artifacts, explicit outcome metadata, blind-aware preflop metrics, profile-aware aggregation, tuning baseline, and Sprint 3 boundary design were all documented and tested.
**Reasoning:** Online rooms and external agents need trustworthy action legality, safe public state, repeatable benchmarks, and event-oriented engine seams before networking is introduced.
**Tradeoffs:** Sprint 2 remained local/terminal-focused longer, and the final benchmark used deeper stacks to complete all 1,000 requested hands after AI tuning; this delays WebSocket prototyping but reduces the risk of building online features on unstable engine/metric semantics.

## 2026-05-09 — Use three separate Codex agents for slice execution review
**Context:** Sprint 3 is migrating terminal output from direct `game.py` prints into `EngineEvent` + `TerminalEventRenderer` through small TDD slices. The user wanted the continuing workflow to include product, engineering, and senior poker-player perspectives, and then clarified that all three roles should be implemented by Codex agents rather than by Hermes role-playing inline.
**Decision:** Document the triad workflow in `docs/triad-role-workflow.md` and require each active `[>]` slice to run through three separate Codex agent sessions: Product Manager Codex Agent for read-only acceptance/non-goal pre-check, Engineer Codex Agent for strict-TDD implementation, and Senior Poker Player Codex Agent for read-only poker realism and terminal UX review. Hermes remains the coordinator and independent verification gate.
**Reasoning:** Separate Codex runs create clearer role isolation and reduce the risk that implementation momentum overrides product scope or player-trust concerns. This is especially important while the project is still a local terminal trainer but is being prepared for a future AI Poker Arena / Agent Poker Platform.
**Tradeoffs:** Each slice now costs more orchestration time than a single engineer run, and read-only review agents may occasionally require another engineer pass. The added friction is intentional for architecture-boundary work where preserving terminal UX, poker semantics, and future agent-readiness matters more than raw speed.
